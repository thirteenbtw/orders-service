# orders-service

REST-сервис для приёма и обработки заказов: каталог товаров, регистрация и вход по JWT, создание заказов с контролем остатков на складе, жизненный цикл заказа и версионируемые миграции базы данных.

**Стек:** Java 21 · Spring Boot 3.3 (Web, Data JPA, Security, Validation) · PostgreSQL 16 · Flyway · JWT (jjwt) · Maven

## Что умеет сервис

- **Каталог товаров.** Просмотр доступен всем, добавление — только администратору.
- **Регистрация и вход.** Пароли хранятся в виде BCrypt-хэшей, после входа выдаётся JWT.
- **Создание заказов.** Заказ из нескольких позиций проверяется на наличие товара и атомарно списывает остатки.
- **Жизненный цикл заказа.** Статусы `NEW → PAID → SHIPPED` и отмена, недопустимые переходы запрещены.
- **Разграничение доступа.** Пользователь видит только свои заказы, администратор — любые.
- **Миграции схемы.** Структура БД создаётся и меняется только через Flyway.
- **Единый формат ошибок.** Любая ошибка возвращается как `{"error": "..."}` с понятным HTTP-статусом.

## Быстрый старт

### Что понадобится

| Инструмент | Версия | Зачем |
|---|---|---|
| JDK | 21 или новее (проверено на 27) | сборка и запуск |
| Maven | 3.9+ | сборка (отдельного `mvnw` в проекте нет) |
| Docker + Docker Compose | любая свежая | PostgreSQL из коробки |

Проверить установку:

```bash
java -version
mvn -v
docker --version
```

### Шаг 1. Запустить базу данных

Из папки `orders-service`:

```bash
docker compose up -d
```

Поднимется PostgreSQL 16 на порту `5432` с базой `orders`, пользователем `orders` и паролем `orders`. Данные хранятся в Docker-томе `pgdata` и переживают перезапуск контейнера.

Если у вас уже есть свой PostgreSQL, Docker не нужен: создайте базу и передайте параметры подключения через [переменные окружения](#настройка).

### Шаг 2. Запустить сервис

```bash
mvn spring-boot:run
```

При старте Flyway сам применит миграции и создаст таблицы, а в каталог попадут три демонстрационных товара. Сервис слушает `http://localhost:8080`.

Проверка, что всё работает:

```bash
curl http://localhost:8080/api/products
```

В ответ придёт JSON со списком товаров.

### Сборка отдельного jar

```bash
mvn clean package
java -jar target/orders-service-1.0.0.jar
```

### Остановка

```bash
docker compose down        # остановить БД, данные сохранятся
docker compose down -v     # остановить БД и удалить все данные
```

## Настройка

Все параметры лежат в `src/main/resources/application.yml` и переопределяются переменными окружения. Значения по умолчанию подходят для локальной разработки.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/orders` | JDBC-адрес базы |
| `DB_USER` | `orders` | пользователь БД |
| `DB_PASSWORD` | `orders` | пароль БД |
| `JWT_SECRET` | `dev-only-secret-change-me-please-32bytes!` | ключ подписи токенов, **минимум 32 байта** |

Срок жизни токена — 60 минут (параметр `app.jwt.ttl-minutes` в `application.yml`). Порт можно сменить переменной `SERVER_PORT`.

> **Важно для продакшена.** Значение `JWT_SECRET` по умолчанию публично известно, потому что лежит в репозитории. Любой, кто его знает, может выпустить токен администратора. Перед развёртыванием обязательно задайте собственный длинный случайный ключ, например:
>
> ```bash
> openssl rand -base64 48
> ```

Пример запуска со своими параметрами (bash):

```bash
DB_URL=jdbc:postgresql://db.example.com:5432/shop \
DB_USER=shop DB_PASSWORD='секрет' \
JWT_SECRET='очень-длинный-случайный-ключ-не-короче-32-байт' \
java -jar target/orders-service-1.0.0.jar
```

То же в PowerShell:

```powershell
$env:DB_PASSWORD = "секрет"
$env:JWT_SECRET  = "очень-длинный-случайный-ключ-не-короче-32-байт"
java -jar target/orders-service-1.0.0.jar
```

## Первый сценарий: от регистрации до заказа

Примеры для bash (Linux, macOS, Git Bash). Пользователям PowerShell см. [заметку ниже](#заметка-для-windows-powershell).

### 1. Регистрация

```bash
curl -X POST http://localhost:8080/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com","password":"password123"}'
```

Ответ `201 Created`:

```json
{ "token": "eyJhbGciOiJIUzM4NCJ9..." }
```

Сохраните токен в переменную:

```bash
TOKEN=eyJhbGciOiJIUzM4NCJ9...
```

Позже можно получить новый токен через `/api/auth/login`.

### 2. Посмотреть каталог

```bash
curl http://localhost:8080/api/products
```

```json
[
  { "id": 1, "name": "Клавиатура механическая", "price": 5990.00, "stock": 25 },
  { "id": 2, "name": "Мышь беспроводная",       "price": 2490.00, "stock": 40 },
  { "id": 3, "name": "Монитор 27\"",            "price": 21990.00, "stock": 10 }
]
```

### 3. Оформить заказ

```bash
curl -X POST http://localhost:8080/api/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"productId":1,"quantity":2},{"productId":2,"quantity":1}]}'
```

Ответ `201 Created`:

```json
{
  "id": 1,
  "status": "NEW",
  "total": 14470.00,
  "createdAt": "2026-10-02T08:15:30.123Z",
  "items": [
    { "productId": 1, "productName": "Клавиатура механическая", "unitPrice": 5990.00, "quantity": 2 },
    { "productId": 2, "productName": "Мышь беспроводная",       "unitPrice": 2490.00, "quantity": 1 }
  ]
}
```

Остаток клавиатур в каталоге уменьшился с 25 до 23, мышей — с 40 до 39.

### 4. Посмотреть свои заказы

```bash
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/orders
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/orders/1
```

### 5. Отменить заказ

```bash
curl -X PATCH http://localhost:8080/api/orders/1/status \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"status":"CANCELLED"}'
```

Заказ получит статус `CANCELLED`, а товары вернутся на склад.

### Заметка для Windows PowerShell

В PowerShell `curl` — это псевдоним `Invoke-WebRequest` со своим синтаксисом. Используйте `curl.exe` или `Invoke-RestMethod`:

```powershell
$reg = Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/auth/register `
  -ContentType 'application/json' `
  -Body '{"email":"user@example.com","password":"password123"}'
$h = @{ Authorization = "Bearer $($reg.token)" }

Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/orders -Headers $h `
  -ContentType 'application/json' `
  -Body '{"items":[{"productId":1,"quantity":2}]}'
```

## Справочник API

Базовый адрес: `http://localhost:8080`. Тело запросов и ответов — JSON (`Content-Type: application/json`). Для защищённых методов нужен заголовок `Authorization: Bearer <token>`.

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| POST | `/api/auth/register` | все | регистрация, возвращает токен |
| POST | `/api/auth/login` | все | вход, возвращает токен |
| GET | `/api/products` | все | список товаров |
| GET | `/api/products/{id}` | все | один товар |
| POST | `/api/products` | `ADMIN` | создать товар |
| POST | `/api/orders` | любой авторизованный | создать заказ |
| GET | `/api/orders` | любой авторизованный | список своих заказов, новые первыми |
| GET | `/api/orders/{id}` | владелец или `ADMIN` | один заказ |
| PATCH | `/api/orders/{id}/status` | владелец (только `CANCELLED`) или `ADMIN` | смена статуса |

### Аутентификация

**`POST /api/auth/register`**

| Поле | Тип | Правила |
|---|---|---|
| `email` | строка | корректный email, обязателен. Приводится к нижнему регистру |
| `password` | строка | от 8 до 72 символов |

Ответы: `201` с `{"token": "..."}`, `400` при невалидных данных, `409`, если email уже занят.

Новый пользователь всегда получает роль `USER`.

**`POST /api/auth/login`**

Поля `email` и `password`. Ответы: `200` с `{"token": "..."}` или `401`, если пара email и пароль неверна. Сообщение одинаково для несуществующего email и неверного пароля, чтобы нельзя было перебирать адреса.

### Товары

**`GET /api/products`** и **`GET /api/products/{id}`** возвращают объект (или массив):

| Поле | Тип | Описание |
|---|---|---|
| `id` | число | идентификатор |
| `name` | строка | название |
| `price` | число | цена с двумя знаками после запятой |
| `stock` | число | остаток на складе |

Для несуществующего `id` — `404`.

**`POST /api/products`** (только `ADMIN`)

```json
{ "name": "Наушники", "price": 3990.00, "stock": 15 }
```

| Поле | Правила |
|---|---|
| `name` | не пустое, до 200 символов |
| `price` | обязательно, не меньше 0 |
| `stock` | не меньше 0 |

Ответ `201` с созданным товаром. Без прав — `403`, без токена — `401`.

### Заказы

**`POST /api/orders`**

```json
{
  "items": [
    { "productId": 1, "quantity": 2 },
    { "productId": 3, "quantity": 1 }
  ]
}
```

| Поле | Правила |
|---|---|
| `items` | непустой список |
| `items[].productId` | обязателен |
| `items[].quantity` | от 1 до 1000 |

Если один и тот же товар указан несколько раз, количества суммируются. Ответ `201` с созданным заказом. Возможные ошибки: `400` (невалидное тело), `404` (товара нет), `409` (не хватает на складе).

**`GET /api/orders`** возвращает массив ваших заказов от новых к старым.

**`GET /api/orders/{id}`** возвращает один заказ. Чужой заказ для обычного пользователя неотличим от несуществующего: в обоих случаях `404`. Так нельзя выяснить, существует ли заказ с таким номером.

**`PATCH /api/orders/{id}/status`**

```json
{ "status": "PAID" }
```

Допустимые значения: `NEW`, `PAID`, `SHIPPED`, `CANCELLED`. Подробные правила — в разделе [Как устроены заказы](#как-устроены-заказы).

### Объект заказа

| Поле | Тип | Описание |
|---|---|---|
| `id` | число | номер заказа |
| `status` | строка | `NEW`, `PAID`, `SHIPPED` или `CANCELLED` |
| `total` | число | сумма всех позиций |
| `createdAt` | строка | время создания в UTC (ISO 8601) |
| `items[]` | массив | позиции: `productId`, `productName`, `unitPrice`, `quantity` |

### Коды ответов и формат ошибок

Все ошибки приходят в виде:

```json
{ "error": "Недостаточно на складе: Монитор 27\" (есть 3)" }
```

Ошибки валидации перечисляют проблемные поля: `{"error": "email: must be a well-formed email address; password: size must be between 8 and 72"}`.

| Код | Когда возникает |
|---|---|
| `200` | успешное чтение или изменение |
| `201` | объект создан |
| `400` | невалидное тело запроса |
| `401` | нет токена, токен просрочен или подделан; неверный логин или пароль. Тело ответа при отсутствии токена пустое |
| `403` | роли не хватает для действия |
| `404` | товар или заказ не найден (в том числе чужой заказ) |
| `409` | конфликт: email занят, нет остатка, недопустимый переход статуса |
| `500` | непредвиденная ошибка. Подробности пишутся в лог сервера, наружу они не отдаются |

## Как устроены заказы

### Статусы и переходы

| Из статуса | Можно перейти в |
|---|---|
| `NEW` | `PAID`, `CANCELLED` |
| `PAID` | `SHIPPED`, `CANCELLED` |
| `SHIPPED` | — (конечный) |
| `CANCELLED` | — (конечный) |

Любая другая попытка вернёт `409 Conflict`, например: `Переход NEW -> SHIPPED недопустим`.

### Кто что может

| Действие | `USER` | `ADMIN` |
|---|---|---|
| Создать заказ | да | да |
| Видеть заказ | только свой | любой |
| Отменить заказ (`CANCELLED`) | только свой | любой |
| Перевести в `PAID` и `SHIPPED` | нет (`403`) | да |

Оплата пока не интегрирована с платёжной системой: статус `PAID` ставит администратор вручную.

### Транзакции и согласованность данных

Главная задача сервиса — не продать то, чего нет на складе, даже при одновременных запросах.

**Создание заказа выполняется в одной транзакции:**

1. Повторяющиеся позиции объединяются, количества суммируются.
2. Нужные товары блокируются через `SELECT ... FOR UPDATE`. Блокировка идёт **в порядке возрастания `id`**, поэтому два заказа с пересекающимися товарами не могут взаимно заблокировать друг друга (дедлок).
3. Для каждой позиции проверяется остаток. Если хоть одной не хватает, выбрасывается ошибка.
4. Остатки списываются, заказ и позиции сохраняются.
5. Если на любом шаге произошла ошибка, откатывается всё. Частично списанных остатков и «осиротевших» заказов не бывает.

**Конкурентные заказы.** Если два покупателя одновременно берут последнюю единицу товара, второй дождётся снятия блокировки, увидит нулевой остаток и получит `409`. Продать один и тот же товар дважды невозможно. Как страховка, в БД стоит ограничение `CHECK (stock >= 0)`.

**Отмена заказа** в той же транзакции возвращает позиции на склад, тоже с блокировкой в порядке `id`.

**Снимок цены.** Название и цена товара копируются в позицию заказа в момент покупки. Если позже цену в каталоге изменят, старые заказы останутся с исходными суммами.

## Авторизация и роли

- **Токен.** После регистрации или входа сервис выдаёт JWT, подписанный алгоритмом HMAC. В нём лежат `id` пользователя, его роль и срок действия (60 минут).
- **Stateless.** Сессий на сервере нет, каждый запрос проверяется по токену. CSRF-защита отключена, потому что аутентификация идёт через заголовок, а не через cookie.
- **Пароли.** Хранятся только как BCrypt-хэши, исходный пароль восстановить нельзя.
- **Публичные эндпоинты:** `/api/auth/**` и `GET /api/products/**`. Всё остальное требует токена.

### Как получить администратора

Регистрация всегда создаёт `USER`. Первого администратора назначают напрямую в БД:

```bash
docker compose exec db psql -U orders -d orders \
  -c "UPDATE users SET role = 'ADMIN' WHERE email = 'user@example.com';"
```

> Роль зашита в токен. После смены роли в БД **нужно войти заново** (`/api/auth/login`) и использовать новый токен, старый останется с прежней ролью до истечения срока.

## База данных и миграции

Схему ведёт Flyway. Файлы лежат в `src/main/resources/db/migration` и применяются автоматически при старте по порядку номеров. Hibernate работает в режиме `ddl-auto: validate`: он только проверяет, что сущности соответствуют схеме, но сам ничего не меняет. Если сущность и таблица разошлись, сервис не запустится и сообщит об этом.

| Миграция | Содержимое |
|---|---|
| `V1__init_schema.sql` | таблицы `users`, `products`, `orders`, `order_items`, индексы, ограничения |
| `V2__seed_products.sql` | три демонстрационных товара |

### Схема

```
users            products           orders                order_items
-----            --------           ------                -----------
id (PK)          id (PK)            id (PK)               id (PK)
email (unique)   name               user_id  → users      order_id   → orders (CASCADE)
password_hash    price (>= 0)       status                product_id → products
role             stock (>= 0)       total                 product_name
created_at                          created_at            unit_price
                                    updated_at            quantity (> 0)
```

Индексы: `orders (user_id, created_at DESC)` для быстрого списка заказов пользователя и `order_items (order_id)`.

### Как добавить миграцию

1. Создайте файл с следующим номером, например `V3__add_order_comment.sql`.
2. Напишите SQL изменения схемы, а затем обновите сущность Java.
3. Перезапустите сервис, Flyway применит новый файл один раз.

**Уже применённые файлы миграций не редактируйте.** Flyway хранит их контрольные суммы, и изменённый файл остановит запуск. Любые правки схемы делайте новой миграцией.

### Полезные команды

```bash
# консоль PostgreSQL
docker compose exec db psql -U orders -d orders

# история применённых миграций
docker compose exec db psql -U orders -d orders -c "SELECT version, description, success FROM flyway_schema_history;"

# полный сброс базы
docker compose down -v && docker compose up -d
```

## Структура проекта

```
orders-service/
├── pom.xml                      зависимости и сборка
├── docker-compose.yml           PostgreSQL для разработки
├── README.md
└── src/
    ├── main/
    │   ├── java/com/thirteenbtw/orders/
    │   │   ├── OrdersApplication.java      точка входа
    │   │   ├── domain/                     сущности: User, Product, Order, OrderItem, Role, OrderStatus
    │   │   ├── repo/                       Spring Data репозитории (в т.ч. блокировка товаров)
    │   │   ├── dto/Dtos.java               запросы и ответы API, правила валидации
    │   │   ├── service/                    бизнес-логика и транзакции
    │   │   ├── security/                   JWT: выпуск, проверка, фильтр, конфигурация
    │   │   └── web/                        REST-контроллеры и обработка ошибок
    │   └── resources/
    │       ├── application.yml             настройки
    │       └── db/migration/               миграции Flyway
    └── test/java/.../domain/OrderStatusTest.java
```

**Слои.** `web` принимает HTTP и ничего не знает о БД, `service` содержит бизнес-правила и границы транзакций, `repo` отвечает за доступ к данным, `domain` хранит сущности и правила переходов статусов.

Сейчас есть юнит-тест на переходы статусов заказа (`OrderStatusTest`, 2 проверки, последний прогон успешный). Интеграционных тестов с реальной БД пока нет.

## Решение проблем

| Симптом | Причина и решение |
|---|---|
| `Connection refused` при старте | не запущен PostgreSQL. Выполните `docker compose up -d` и подождите несколько секунд |
| `password authentication failed` | `DB_USER` или `DB_PASSWORD` не совпадают с настройками БД |
| `port 5432 is already allocated` | порт занят другим PostgreSQL. Остановите его или смените порт в `docker-compose.yml` и в `DB_URL` |
| `Port 8080 was already in use` | порт занят. Задайте другой: `SERVER_PORT=8081` |
| `Schema-validation: missing table` | миграции не применились. Проверьте `flyway_schema_history` или сбросьте базу |
| `Migration checksum mismatch` | вы изменили уже применённую миграцию. Верните исходное содержимое или сбросьте локальную БД |
| `The specified key byte array is N bits which is not secure enough` | `JWT_SECRET` короче 32 байт |
| `invalid target release: 21` | установлена старая версия JDK, нужна 21 или новее |
| `mvn` не найден сразу после установки | переменные `PATH` и `JAVA_HOME` подхватываются только новыми окнами терминала. Откройте новое окно |
| Maven: `Connection reset` или `Could not transfer artifact` | доступ в интернет идёт через прокси, а Maven переменные `HTTP_PROXY` не читает. Передайте прокси явно (пример ниже) или пропишите его в `~/.m2/settings.xml` |
| `401` на защищённом методе | нет заголовка `Authorization: Bearer ...`, токен просрочен (60 минут) или секрет сменился после перезапуска |
| Стал админом, а `403` | роль зашита в токен, войдите заново и используйте новый токен |
| В PowerShell `curl` ругается на `-H` или `-d` | используйте `curl.exe` или `Invoke-RestMethod` (см. [заметку](#заметка-для-windows-powershell)) |

### Maven за прокси

Пример для PowerShell, где прокси слушает `127.0.0.1:10809` (подставьте свой адрес). Настройка действует только в текущем окне:

```powershell
$env:MAVEN_OPTS = "-Dhttp.proxyHost=127.0.0.1 -Dhttp.proxyPort=10809 -Dhttps.proxyHost=127.0.0.1 -Dhttps.proxyPort=10809"
mvn "-Dmaven.resolver.transport=wagon" test
```

Ключ `-Dmaven.resolver.transport=wagon` нужен, потому что встроенный транспорт Maven 3.10 в такой конфигурации выдавал `Connection reset`, а с `wagon` зависимости скачались.

Постоянный вариант — файл `~/.m2/settings.xml`:

```xml
<settings>
  <proxies>
    <proxy>
      <id>local</id>
      <active>true</active>
      <protocol>http</protocol>
      <host>127.0.0.1</host>
      <port>10809</port>
    </proxy>
  </proxies>
</settings>
```

## Ограничения и планы

Что сейчас не реализовано:

- интеграция с платёжной системой (статус `PAID` ставится вручную);
- пагинация и фильтры в списках;
- редактирование и удаление товаров, управление пользователями через API;
- интеграционные тесты с Testcontainers;
- OpenAPI/Swagger-документация;
- refresh-токены и отзыв токенов;
- идемпотентность создания заказа (повторный POST создаст второй заказ);
- Dockerfile для самого сервиса.
